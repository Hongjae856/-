# PTP 라인 IDT — 파우치 방식 전환 계획 (11/17 작성)

## 1. 결정 사항 (사용자 선택 11/17)
| 항목 | 결정 |
|---|---|
| 전환 순서 | PTP 통합 먼저 → 병 라인(포장라인 추가 포함)은 그다음 |
| 원칙 | 하드웨어(설비 형상 · 치수 · 동작 · 절차 내용)는 유지, 진행 방식(1인칭 · 작업자 선택 · 모드 · 자유 · 시연 · OEE 대시보드 · 이상사례 교육)은 파우치와 같게. UI 를 그대로 베끼는 것은 아님 |
| 설비 형상 | 파우치 엔진(Three.js)으로 이식 — PTP 형상 코드를 읽어 변환하는 층을 둠 |
| 두 판 | 방 모드 · 단일 화면을 하나로 합침 (기존 두 판은 더 이상 갱신하지 않음) |
| 방 배치 | 단일 화면판 배치 유지 (공용 mm 좌표 · 칸막이 벽 x=0 · 연결 컨베이어 수평 직선 · 배출 높이 1,290 mm) |
| 남길 PTP 기능 | 교체부품(체인지파트) 과정만 (SMED · AI 교관 · 교관용 결과 취합 · 진행 저장은 제외) |
| 이상사례 | OEE 시트의 블리스터 라인 부동사유 기록에서 사례 추출 · 부동시간 · 빈도 · 중요도 정렬 (시트 읽기 범위를 PTP 까지 넓힘) |
| 게시 | 새 아티팩트 (기존 PTP 아티팩트 4종은 그대로 둠) |

## 2. 구조 (안)
- **셸 = 파우치 엔진** : Three.js 장면 · 1인칭(fps) · 작업자 선택 · 교체(crew) · 자유모드(free) · 시연 · OEE 공통 모듈(`oee/`) · 이상사례 교육(edu) · 모니터 HMI 텍스처(hmitex) · 경광등 등
- **PTP 두 앱(충전기 `src/filler.html` · 포장라인 `src/line.html`)** : 과정 단계 · HMI 화면 · 시뮬레이션 · 알람 · 교체부품 내용은 원본에서 그대로 사용 (원본 파일은 고치지 않고 빌드 때 주입 — `ptp_one` 방식 승계)
- **형상 다리** : 두 앱이 매 프레임 만드는 정점 버퍼(공용 mm, 위치 · 법선 · 색 · 금속도)를 Three.js BufferGeometry 로 옮겨 그림 → 1인칭 · 그림자 · 재질을 파우치와 같은 렌더러로
- 빌드 : `ptp3/build.py` → `PTP라인_IDT.html` · 버전 이력 `ptp3/changelog.js` (CLAUDE.md 에 첫 게시 후 등록)

## 3. 단계
| 단계 | 내용 | 완료 기준 |
|---|---|---|
| P1 | 형상 이식 · 한 장면(두 실) · 1인칭 이동(장애물 · 칸막이 벽) | 두 설비가 Three.js 로 원본과 같은 모양 · 동작, 1인칭으로 걸어 다님 |
| P2 | 메인화면(모드 → 작업자) · 작업자 교체 · 과정 연결(기본 · 심화 학습/평가 · 교체부품) | 두 실 과정이 끝까지 진행(회귀 시험) |
| P3 | 설비 화면을 모니터 유리면에 표시 · 1인칭에서 다가가 직접 조작 · 판넬 실제 버튼 | 팝업 없이 1인칭 조작으로 과정 진행 |
| P4 | 자유모드(순서 · 감점 없음 · 인터록 해제 · 문 · 덮개) · 시연모드(작업자별) | 파우치와 같은 동작 |
| P5 | OEE 대시보드(블리스터 범위) · 이상사례 대처 교육(부동사유 기반) | 실제 OEE 값은 IDT DB 에만 저장 (저장소 · 게시 페이지에 넣지 않음) |
| P6 | 작업자 동작 현실성 전수 점검 · 자연 변동 · 자재 소모 · 회귀 · 게시 | 점검표 · 시험 결과 보고 |

## 4. 위험 · 확인 필요
- 두 앱이 매 프레임 형상을 다시 만드는 비용 → 정적 부분 캐시 필요 여부는 P1 에서 측정
- 앱 HMI 는 iframe 안의 DOM → 모니터 유리면 표시 방식은 P3 에서 확인
- PTP 작업자 모델 · 작업자 동선은 원본에 없거나 단순함 → 파우치 작업자 모델로 새로 구성
- OEE 시트에서 블리스터 라인 부동사유 항목 구성 [확인 필요]
